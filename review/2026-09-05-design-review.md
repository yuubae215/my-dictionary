## 0. 総評

- **構造の質は高い。** 恒久IDと採番の分離、概念と現場語の二層、対象語彙とメタ語彙の分離基準（「登場人物を主語にして言えるか」）、3段判定、集計ドリフトの検出という一連の仕組みは、辞書を「引くもの」かつ「保守できるもの」にしており、社内ドラフトとしては異例の水準にある。
- **一方、動機に対する答えは半分しか出ていない。** 辞書は「座標系を明示せよ」（参照座標系・ローカル／ワールド・ハンドネス・回転表現規約）という**数値化された空間**の視点依存には答えているが、動機の例として挙げられている「**右と言っても誰から見て右か**」——つまり**言語で語られる方向**（右・左・手前・奥・表・裏・上流・下流）の視点依存には、概念も現場語も1件もない。§1で詳述する。

## 1. 動機（視点依存・ドメイン差）に対する到達点

### 1.1 Clause 4「+X 前方、Y 左、Z 上」は主語を欠いている（最重要）

第2編 Clause 4（原辞書3章）は空間座標系を「+X 前方、Y 左、Z 上、右手直交座標系（ROS REP-103 準拠）」と定める。しかし ROS REP-103 は**ボディフレーム**（x forward, y left, z up）と**ワールドフレーム**（ENU: x east, y north, z up）を区別しており、「前方」はボディ（ロボット・車両・機械）に固有の内在的な向きである。**ワールド空間（第2編3.9）には「前方」がない。** カメラの光学フレーム（REP-103: z forward, x right, y down）も別の規約である。

これは、まさに動機が挙げる「誰から見て」の問題が**基礎規約そのものの中で未解決**であることを意味する。現状の記述では、
- 「架台・床」のワールド座標系の +X がどちらを向くかが決められない（東？ ラインの流れ方向？）。
- ロボットベース座標系の「前方」と、作業者が正面に立ったときの「手前」が逆向きになる。
- ビジョンカメラの出力（第2編3.5 pose の主語）が REP-103 の光学フレームなら Z が前方であり、Clause 4 と矛盾する。

**推奨:** Clause 4 の「空間座標系」行を3行に分ける——(a) ワールド座標系（原点＝架台・床の基準、+X＝ラインの流れ方向 or 東 のいずれかを規定、Z 上）、(b) 装置ボディ座標系（+X 前方、Y 左、Z 上。「前方」の定義は装置ごとに附属書で規定）、(c) 光学／センサ座標系（REP-103 optical frame）。あわせて第2編3.1／3.2 の EXAMPLE をこの3種で書き分ける。

### 1.2 「方向の参照枠」概念がない

「右」「左」「手前」「奥」「上流」「下流」「表」「裏」は現場で最も頻繁に口にされる空間語だが、辞書には概念も現場語も存在しない（grep 結果: 該当0件）。言語学では方向表現の参照枠が3種に分かれることが確立している（Levinson, *Space in Language and Cognition*, 2003）。

| 参照枠 | 意味 | 工場での例 |
| :--- | :--- | :--- |
| 内在的 (intrinsic) | 対象自身が持つ前後左右 | 「機械の正面」「ロボットの右アーム」「ワークの表面」 |
| 相対的 (relative) | 観察者から見た右左 | 「（作業者から見て）右のトレー」——立ち位置で反転する |
| 絶対的 (absolute) | 環境に固定された軸 | 「上流／下流」「東側」「Z上（重力）」 |

「右」の取り違えは、話者が相対的枠で言い、聞き手が内在的枠で解釈したときに起きる。**この3分類を1エントリとして立て、現場語「右／左／手前／奥／上流／下流」を、主語（登場人物）と参照枠を伴って附属書Aに収録する**ことが、動機に対する最も直接的な答えになる。

位置づけの候補: 第2編 II-A（座標系そのもの）の直後、または全編附属書F.5 が「未収録」としている **`Integration × Station`（セル原点・ステーション座標系）**。ステーションの内在的枠（正面・上流側）を定義することが、この空セルの実体である。

### 1.3 離散的な向き（表裏・正逆・向き不問）が未収録

原辞書2.1節の同音異義表は「姿勢／向き」のPLC文脈の意味を「ワークの表裏・正逆フラグ」と自ら挙げている。また第3編3.15 状態期待値の EXAMPLE は「向き不問」「向き既知」を使っている。しかし、**姿勢を連続値（第2編3.5 pose）ではなく離散区分（表／裏、正／逆、N回対称の何番目か）として扱う概念は辞書にない。** 対称性ルール（第3編3.12）が「同一とみなせる回転角度」を定めるのに対し、その同値類に現場が付ける名前（表・裏）を受ける語彙が欠けている。

**推奨:** 「離散姿勢区分（discrete orientation class）」を第2編 II-B または第3編 III-C に新設し、pose（連続）／symmetry rule（同値関係）／state expectation（「向き不問」）の三者をつなぐ。現場語: 表／裏、正／逆、向き不問。RAMI: `Integration / Product / Type & Instance` が自然。

### 1.4 同音異義が現場語モデルに載らない（構造的な問題）

附属書Aの不変条件は「各現場語は**ちょうど1つの代表形**を持つ」である。この規則のもとでは、原辞書2.1節が動機の筆頭に挙げる「原点」（CAD絶対原点／TCPオフセット／治具突き当てピン位置・センサON位置）や「クリアランス」「姿勢」は、代表形が複数あるため**現場語として登録できない**。実際、これらは附属書A・G.7 のどこにも現れず、2.1節の表は辞書本体と接続されていない。

つまり **「同じ言葉が違う意味を持つ」問題を解くための辞書が、同じ言葉を複数の意味で登録する手段を持っていない。** ISO 704 / ISO 10241-1 の流儀では、同綴異義語（homograph）は文脈ラベル付きの別エントリ（例:「原点〈CAD〉」「原点〈PLC〉」）として登録する。

**推奨:** 現場語の一意性を「語」単位から「（語, 主語）」の組単位へ改める。現場語はすでに「ちょうど1つの主語」を持つため、`原点（主語: CADシステム・PLM）→ 第2編3.9 world space`、`原点（主語: 治具）→ 第2編3.14 datum reference feature`、`原点（主語: エンドエフェクタ）→ 第3編3.11 grasp specification` のように、同じ語を主語違いで複数登録できる。2.1節の3語（原点・姿勢・クリアランス）とD-2026-08-22-14 の「インタフェース」をまず登録する。これにより第M編3.10（同音異義）の EXAMPLE が附属書Aの実データに接続する。

### 1.5 pose（第2編3.5）と spatial representation（第2編3.7）の重なり

- pose の定義文「位置（並進）と向き（回転）を組み合わせた空間的状態」には**参照座標系が現れない**。ISO 8373:2021（Robotics — Vocabulary）は pose とともに base／tool／world の各座標系を語彙として持ち、姿勢値は常にそれらの座標系に対して読まれる。動機（視点依存）から言っても「参照座標系を伴わない pose は値として成立しない」ことを定義文に入れるべきである。
- 新設の spatial representation は「対象の位置・姿勢を、ある参照座標系を基準として表した**値**」であり、pose と実質的に同じ概念を指している。2つの見出し語が同じ概念を画定していれば、それは辞書内の異音同義（第M編3.11）であり、3段判定の「統合」の前例になりうる。
- さらに、その子概念 local space／world space の定義文の genus は「**空間**」（「…として表現される空間」）であり、親の genus「**値**」と一致しない（§2.3）。

**推奨:** (a) pose の定義文に「ある参照座標系（3.2）に対する」を加える。(b) spatial representation は、pose の「参照座標系の取り方」というファセットに落とすか、local／world の genus を「参照座標系を明示した位置・姿勢の表現」に揃えて pose を親にするか、いずれかに統一する。現状の3層（pose／spatial representation／local・world）は読み手に2つの上位概念を提示している。

### 1.6 参照規格の欠落

動機に直結する規格が Clause 2 に見当たらない。
- **ISO 8373:2021** Robotics — Vocabulary（pose・base／tool／world coordinate system の正式定義。ISO 9787 は座標系の配置規約であり語彙規格ではない）。
- **ISO 19111** Geographic information — Referencing by coordinates（「座標系＝軸の集合」と「座標参照系＝座標系＋データム」を分ける枠組み。第2編3.1／3.2 の区別と同型であり、命名の裏づけになる）。
- **ISO 80000-3** Space and time（量と単位）。Clause 4 の単位規定の典拠。
- **ISO 10241-1:2011** Terminological entries in standards（§2参照）。

## 2. ISO 704 / ISO 10241-1 / Directives Part 2 への準拠

### 2.1 admitted term の誤用

ISO 10241-1 において admitted term は**同一概念を指す同義語**であり、値・下位概念・旧称（deprecated）とは区別される。次の箇所は規約に反する。

| 箇所 | 現状の admitted term | 問題 |
| :--- | :--- | :--- |
| 第2編3.3 handedness | right-handed / left-handed | 概念の**値**であり同義語ではない |
| 第2編3.11 distance metric convention | metric／Minkowski距離（L1・L2・L∞） | Minkowski距離は規約ではなく距離族。値の列挙 |
| 第4編3.2 dimension-raising operation | 掃引操作／sweep operation（**下位概念**。Note 3参照） | 自ら下位概念と書いている。admitted term は同義語のみ |
| 第3編3.13 v&v level | 検証ステータス（旧和文名） | 旧称は DEPRECATED として別記する |
| 第1編3.8 interaction interface | 関与インタフェース分類（原1.07の旧和文名） | 同上。しかもこの旧称は別概念（3.7）の名であった |
| 第M編3.13 | freshness guarantee（原辞書の英語主名称） | 同上 |
| 第1編3.7 | 人・機械の2軸 | 説明句であり用語ではない |

**推奨:** エントリ書式に `DEPRECATED:` 行を追加し、旧称はそこへ移す。値・下位概念は Note へ移す。

### 2.2 定義文に要件・比較・自己言及が含まれる

Directives Part 2 は「定義は要件の形をとってはならず、要件を含んではならない」と定める。ISO 704 は定義を「上位概念＋区別的特性」の一文で、他概念との比較や否定に依存せず書くことを求める。

| 箇所 | 定義文中の該当部分 | 種別 |
| :--- | :--- | :--- |
| 第3編3.3 derived value | 「入力値（3.2）と明確に区別する。」 | 要件 |
| 第3編3.6 instance identifier | 「発番権限は単一システムに限定される」 | 要件（設計原則 M.14 の内容） |
| 第4編3.3 measurement | 「新しい幾何要素を生まない点で3.2と異なり」 | 他概念との比較 |
| 第2編3.1 coordinate system | 「本仕様書ではClause 4に従い右手系の…」「本編の他のエントリ…は下位概念である」 | 自己言及・注記内容 |
| 第2編3.16 exclusion zone | 「接触・侵入してはならないと定義された」 | 要件の引用（これは可。「〜と定義された領域」は特性） |

要件・比較・自己言及は Note へ移し、定義文は genus＋differentia の一文に純化する。

### 2.3 genus の不一致（新設親概念で2件、既存で1件）

| 親 | 親の genus | 子 | 子の genus | 判定 |
| :--- | :--- | :--- | :--- | :--- |
| 第2編3.7 spatial representation | 値 | 3.8 local space／3.9 world space | 空間 | **不一致**（§1.5） |
| 第4編3.1 geometric operation | 幾何要素を入力として…得る**操作** | 3.2 dimension-raising operation | **設計パターン** | **不一致** |
| 第3編3.1 value | 情報 | 3.2／3.3 | 情報 | 一致 |
| 第3編3.4 identifier | 記号 | 3.5／3.6 | 識別子 | 一致 |
| 第M編3.4 model element | 要素 | 3.5 entity（実体）／3.6 value object（データ） | ほぼ一致 | 許容 |
| 第M編3.9 term–concept mismatch | 状態 | 3.10／3.11 | 状態 | 一致 |

第4編3.1／3.2 には矛盾がもう1段ある。3.2 の Hierarchy Level を `N/A` にした根拠は「設計パターンであり、**幾何以外にも適用される**」（Note 5、EXAMPLE 2 はモデリング手順への適用）である。幾何以外にも適用されるなら、それは「幾何要素に対する操作」の下位概念ではない。**is-a を維持するなら EXAMPLE 2 と N/A 提案を撤回し、N/A を維持するなら親を「次元上昇パターン一般」に改めて geometric operation との is-a を外す**、どちらかに決める必要がある。

### 2.4 refers-to の比率

確定関係の内訳（Note 2 の行数ベース）: refers-to 約200件に対し、is-a 15・constrained-by 2・transforms 2・part-of 1。**9割以上が型情報を持たない refers-to** であり、原辞書5章冒頭が「既知の弱点」とした状態から実質的には進んでいない。ISO 704 は連想関係にも意味を与える（原因–結果、活動–道具、生産者–生成物など）。全編附属書C.4 の追加条件は妥当だが、少なくとも次の3型は既に定義文レベルで根拠がある: `expressed-in`（値→参照座標系）、`governed-by`（値→規約: 2.04／2.06／2.10）、`evaluated-against`（値→期待値・レベル）。

### 2.5 「IRDI」という呼称

IRDI（ISO/IEC 6523 の ICD ＋ ISO 29002-5）は登録機関識別子を含む3部構成であり、`eed:0001#001` は IRDI ではない（8.9節も「同じ考え方」と留保している）。外部共有時の誤解を避けるため、本文では「恒久ID（IRDI 型）」または「EED-ID」と呼び、附属書G.9 に「正式な IRDI ではない」と明記することを推奨する。将来 ECLASS／IEC CDD へ登録する際は RAI を得て振り直す前提になる。

## 3. 分類設計（RAMI 4.0 3軸）

### 3.1 Communication 層の欠落

RAMI 4.0（DIN SPEC 91345）の Layers 軸は **Business／Functional／Information／Communication／Integration／Asset の6層**である。原辞書4.1節と全編附属書F.1 は5値とし、F.4 は「RAMI 4.0の5層すべてに最低1件ある」を CE 成立の根拠にしている。Communication 層は辞書本文に1度だけ登場する（第3編3.16 event の EXAMPLE「Communication層を経てInformation層へ報告される」）が、軸の値としては存在しない。

これは「適用範囲外」として明示すれば MECE の主張は保てる（通信規格に依存しないという Clause 1 の方針と整合する）。**黙って落としている現状は、F.5 の原則「空であることを黙っておくと網羅したという誤解を生む」に自ら反している。** 6値に改め、Communication 行を「適用範囲外（通信規格・プロトコルに依存しない方針による）」として空セル一覧に載せることを推奨する。

### 3.2 Hierarchy Level の N/A 増殖は「概念種別」の欠落

対象語彙50件のうち8件が `N/A（メタ概念）` であり、しかも同型の概念で値が割れている。

| 概念 | Hier. Level | 備考 |
| :--- | :--- | :--- |
| 第2編3.1 coordinate system | N/A | 数学的枠組み |
| 第2編3.3 handedness | **Product** | 同じく数学的規約なのに Product |
| 第2編3.4 unit scale convention | **Product** | 3.11 Note 3 が「同じ型の落とし穴」と呼ぶ3規約のうち |
| 第2編3.6 rotation representation convention | **Product** | 〃 |
| 第2編3.11 distance metric convention | N/A | 〃 ——3規約で Product／Product／N/A と割れている |

根本原因は、辞書が**種別の異なる概念**——物（bounding volume）、値（pose）、操作（coordinate transformation）、規約（unit scale convention）、設計原則（M-D）、分類体系（work interface）——を同じ3軸で分類していることにある。Hierarchy Level は「物」と「場所」には意味を持つが、規約や原則には本来適用されない。

**推奨:** 附属書Bに「概念種別」列（object／value／operation／convention／classification／principle）を追加し、Hierarchy Level は object・value にのみ適用、convention・principle は種別側で `N/A` を導出する。これで N/A が判断ではなく規則から出るようになり、3規約の不揃いも解消する。

### 3.3 責務タグの排他性（F-20 の補足）

F-20 は `原4.04` の `[設備制御]` が P と C の両方にある1件を挙げているが、より一般的な問題として、`[共通アーキテクチャ]` は「常に P としてのみ現れ C として現れない」と0章が規定するのに対し、第2編3.1／3.7 など「規約を定める側」が `MetaArchitecture` を P に持つ一方で、その規約を「使う側」の中に `MetaArchitecture` がいないことは自明でない（共通アーキテクチャは契約境界の利用者でもある）。排他性を決める際は、この非対称の根拠も併せて0章に書くべきである。
